### P0-3 Prise de contrôle d'un compte par pré-inscription (vérifié à la lecture)

`api/main.py:420-433` : si un compte existe en `pending_email`, une nouvelle
inscription sur la même adresse réémet un jeton **mais conserve le
`password_hash` de la première inscription**.

Scénario :

1. L'attaquant s'inscrit avec l'adresse d'un collègue (ou d'une adresse de
   `ADMIN_EMAILS`, publiques dans le dépôt) et son propre mot de passe.
2. La victime s'inscrit plus tard : 201, un lien de confirmation lui est
   envoyé ; son mot de passe est ignoré.
3. La victime clique : le compte passe `pending_admin_activation` (ou
   directement `admin` actif pour `ADMIN_EMAILS`, `accounts_repository.py:40-43`).
4. L'attaquant se connecte avec son mot de passe. Même si la victime fait
   ensuite « mot de passe oublié », le cookie de l'attaquant reste valide
   30 jours (P1-2).

**Correctif minimal** (`auth_signup`) :

```python
    else:
        user = existing
        # Le dernier à s'inscrire fixe le mot de passe : seul le détenteur
        # de la boîte mail pourra confirmer, et il confirme SON mot de passe.
        user.password_hash = accounts.hash_password(body.password)
        repo.db.commit()
        repo.invalidate_outstanding_tokens(user.id, "confirm_email")
```

**Correctif robuste** : ne jamais fixer le mot de passe avant la preuve de
possession de l'adresse — soit le stocker sur le jeton
(`EmailToken.pending_password_hash`, colonne nullable, ajoutée
automatiquement par `_ajouter_colonnes_manquantes`) et l'appliquer dans
`auth_confirm_email`, soit faire choisir le mot de passe sur la page de
confirmation (même parcours que la réinitialisation). Dans tous les cas,
incrémenter la version de session (P1-2) à la confirmation.

## 4. P1 — important

### P1-1 Cookie de session sans `Secure`, pas de HSTS (vérifié)

`api/main.py:489-492` : `set_cookie(..., httponly=True, samesite="lax")`,
sans `secure=True`. Aucun en-tête `Strict-Transport-Security` (ni FastAPI,
ni `frontend/nginx.conf.template`). Sur un réseau hostile (Wi-Fi), une
requête `http://` fait partir le cookie en clair.

```python
_COOKIE_SECURE = os.environ.get("CAL_IUT_COOKIE_SECURE", "1") != "0"
response.set_cookie(..., httponly=True, samesite="lax", secure=_COOKIE_SECURE)
```

(`CAL_IUT_COOKIE_SECURE=0` en développement local, et dans `conftest.py`.)
Dans `nginx.conf.template` : `add_header Strict-Transport-Security "max-age=31536000" always;`
(à vérifier : si Traefik/Dokploy termine TLS, l'y poser plutôt).

### P1-2 Sessions non révocables (vérifié)

`accounts.py:103-124` : le cookie ne porte que `user_id.expiration.signature`.
Ni `reset-password` (`main.py:535-556`), ni `logout` (`:496-499`) ne
l'invalident : un cookie volé reste valable 30 jours après changement de mot
de passe. La désactivation, elle, est bien relue à chaque requête.

Correctif : colonne `User.session_version` (int, nullable, défaut 0), incluse
dans le jeton signé (`f"{user_id}.{version}.{expiry}"`), comparée dans
`get_current_user` et `require_auth`, incrémentée à la réinitialisation, à la
confirmation d'email et sur un bouton « déconnecter partout ».

### P1-3 Aucune limitation de débit sur les routes publiques d'authentification (vérifié)

Aucun limiteur (recherche `slowapi`, `limit_req` : rien).

- `/auth/login` : force brute illimitée ; chaque essai coûte un hachage
  Argon2 (64 Mo par défaut) : quelques dizaines de requêtes parallèles
  suffisent à saturer la mémoire du conteneur.
- `/auth/signup` : chaque appel envoie un mail de confirmation à une adresse
  arbitraire (`main.py:420-456`, réémission sur `pending_email`) : envoi de
  mails en masse au nom du domaine, quota Resend, réputation d'expéditeur.
- `/auth/forgot-password` : même abus sur les comptes actifs.

Correctif simple (un seul worker uvicorn, état en mémoire acceptable) :

```python
_ESSAIS: dict[str, deque] = defaultdict(deque)
def _limiter(cle: str, max_essais: int = 5, fenetre_s: int = 300) -> None:
    maintenant = time.monotonic()
    file = _ESSAIS[cle]
    while file and maintenant - file[0] > fenetre_s:
        file.popleft()
    if len(file) >= max_essais:
        raise HTTPException(429, "Trop de tentatives, réessayez plus tard.")
    file.append(maintenant)
```

appelé avec `f"login:{email}"`, `f"signup:{email}"`, `f"forgot:{email}"` et
l'IP cliente. Pour l'IP derrière nginx : lancer uvicorn avec
`forwarded_allow_ips="*"` (réseau Docker interne) — à vérifier selon la
chaîne Traefik/nginx.

### P1-4 État global muté sans verrou : double réservation et mises à jour perdues (vérifié à la lecture)

Les routes d'écriture sont des `def` synchrones, exécutées en parallèle dans
le pool de threads de Starlette. `AppState.timetable` est modifié tantôt par
réaffectation (`deposer.py:20`, `main.py:1300`, `:5526`, `regen.py:310`),
tantôt en place (`main.py:5014` `append`, `:5042` `remove`, `:5565`).
Aucun verrou n'entoure la séquence « valider puis écrire ».

Scénarios :

1. Deux personnes posent deux séances différentes dans la même salle au même
   créneau : les deux validations passent, les deux écritures aussi.
2. Un `append` sur l'ancienne liste pendant qu'un autre thread réaffecte
   `state.timetable` : le placement disparaît de la mémoire (il reste en base,
   réapparaît au redémarrage) et n'est plus vu par les contrôles de conflit.
3. `POST /regen/week` lit `state.timetable` (`regen.py:218`), résout 90 à
   150 s, puis réécrit les séances de sa portée (`regen.py:310`) : un
   déplacement manuel fait pendant le calcul est écrasé.
4. `solve_async` (`main.py:1341-1345`) ne vérifie pas qu'une régénération
   tourne ; `POST /solve` synchrone ne prend aucun verrou.

Correctif : un verrou unique d'écriture planning.

```python
_verrou_planning = threading.RLock()

def verrou_planning():
    with _verrou_planning:
        yield

# sur chaque route d'écriture planning / MCP apply :
dependencies=[Depends(accounts.require_role("edit")), Depends(verrou_planning)]
```

Pour la régénération : ne pas tenir le verrou pendant la résolution, mais le
prendre pour la fusion finale et abandonner si une séance de la portée a
bougé depuis l'instantané (`placement_by_session`). Faire vérifier
`_current_regen_job` par `solve_async`, et `_job_lock` par `/solve`.

### P1-9 Un moteur SQLAlchemy recréé à chaque requête, sessions jamais fermées (vérifié)

`api/state.py:68-70` : `get_repo()` appelle `init_db()` à chaque appel, qui
appelle `get_engine()` (`db/session.py:19-26`) : **nouveau moteur et nouveau
pool** à chaque fois, puis `create_all` et l'inspection de toutes les tables.
Mesuré : 5,8 ms par appel, 198 moteurs distincts pour 200 appels. `get_repo()`
est appelé 25 fois dans `main.py`. Les `Session` créées par
`PlanningRepository(get_db(...))` et `_account_repo()` ne sont jamais
fermées (seul `mcp/auth.py:88-89` le fait).

Correctif : `init_db()` une seule fois dans `startup()` ; `get_repo()` ne fait
plus que `PlanningRepository(get_db(path))` ; fermeture par dépendance
FastAPI :

```python
def repo_dep():
    db = get_db(get_state().db_path)
    try:
        yield PlanningRepository(db)
    finally:
        db.close()
```

Activer aussi le mode WAL et un délai d'attente (deux processus écrivent :
`backend` et `celcat-nuit`) :

```python
@event.listens_for(engine, "connect")
def _pragmas(conn, _):
    conn.execute("PRAGMA journal_mode=WAL")
    conn.execute("PRAGMA busy_timeout=10000")
```

### P1-10 Pas de sauvegarde de la base SQLite (vérifié)

Les « sauvegardes » (`api/sauvegardes.py`) sont des instantanés JSON des
placements, écrits **dans le même volume** (`data/state/sauvegardes/`). La
base elle-même (comptes, clés MCP, tâches, corrections, historique des runs)
n'est sauvegardée nulle part, et aucune procédure n'est documentée
(`GUIDE.md`, `docs/`). Perte du volume Dokploy = perte de tout.

Correctif : sauvegarde quotidienne cohérente et externalisée, par exemple
dans le script du conteneur `celcat-nuit` ou une tâche Dokploy :

```bash
sqlite3 /app/data/state/cal-iut.db ".backup '/app/data/state/backup/cal-iut-$(date +%F).db'"
```

puis copie hors serveur (sauvegarde de volume Dokploy vers S3, ou `rclone`),
rétention 30 jours, et un test de restauration documenté dans `GUIDE.md`.

### P1-14 Fichiers d'état écrits par deux conteneurs sans verrou inter-processus (à vérifier)

`celcat_sync.json` (journal séance vers `event_id`, « seul rempart contre les

(`celcat/sync.py:57-129`, `nuit.py:1471-1486`). L'écriture est atomique,
mais pas la séquence lecture-écriture : si les deux se chevauchent, la ligne

recréerait l'évènement dans Celcat (doublon). Fenêtre courte (millisecondes),
non reproduite ici.

Correctif : verrou `fcntl.flock` sur un fichier `celcat_sync.lock` autour de
chaque `charger()`/`sauver()` (fonction `modifier(fn)` dans `etat.py`).

## 7. Points solides

- Inventaire des routes au démarrage (`_verifier_couverture_auth`) : une
  route oubliée fait échouer le lancement plutôt que de devenir publique.
- Toutes les routes d'écriture portent un `require_role` (vérifié par
  introspection) ; rôle et statut relus en base à chaque requête.
- Argon2 pour les mots de passe, jetons à usage unique stockés hachés,
  clés MCP hachées (SHA-256 sur 256 bits aléatoires : suffisant),
  comparaison à temps constant du jeton d'environnement.
- Mot de passe caviardé des erreurs 422 (`main.py:209-227`).
- Téléchargement de sauvegarde protégé contre la traversée de chemin
  (`sauvegardes.py:45-55`, `strptime` strict).
- Mot de passe VPN passé par l'entrée standard à openconnect
  (`celcat/reseau.py:289`).
- File Celcat en un fichier par job, écritures atomiques côté Celcat.
